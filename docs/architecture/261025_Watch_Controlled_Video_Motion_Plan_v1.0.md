## 1. Authority, baseline, and deliverable

The first useful analysis is synchronized replay, wrist-signal charts, and editable per-attempt forehand/backhand/unclassified and clean/mishit/unsure reference labels. Original audio preserves spoken labels; the owner corrects/matches them manually. No transcription dependency, automatic shot detector, technique/quality grade, cloud AI, professional imports, guests, or GPS is included.

## 3. One combined protocol, explicit device facts

Keep the existing motion/Health state machines. Add one pure shared `VideoMotionSession` reducer for coordination plus one adapter per device. Separate observed facts (`phoneWriting`, `motionDurable`, `peerUnknown`, `locallyFinalized`, `motionReceiptVerified`) from the derived combined presentation. The phone owns camera/media; Watch owns motion and local Stop. Neither device may invent the other's saved/recording state.

Every envelope includes schema, operation ID, session ID, reserved recording ID, owner/practice ID, accepted preparation revision, phone/Watch installation epochs, arm generation, sender run/clock epoch, command sequence and expected state revision. Bound byte size, arrays, pending requests and execution time; reject unknown versions, mismatches and malformed/nonfinite values. Persist accepted operation/result transitions before acknowledging effects. Repeated identical IDs return the recorded outcome; conflicting duplicate payloads fail. Terminal sessions never reopen. Old-epoch/start messages cannot begin a new set after cancel, deletion, restart or re-arming.

**Preflight and arm:** On iPhone select “Video + motion”, frame the owner with a stable rear camera, request camera/microphone permissions locally, show preview and remaining storage, and tap “Ready for Watch”. Record actual format/orientation; initial ratifiable default is rear wide camera, landscape guidance, 1080p/30 fps with audio, conditional on supported formats and measured device behavior. No silent format downgrade. Permission denial gives a useful normal motion-only path; the combined mode requires both video and audio. Do not collect microphone data while merely previewing. Disable idle sleep only while the camera preparation/recording screen is active; restore it on every exit.

Arm requires foreground-active scene, authorized/available camera and microphone, running preview, writable private staging, adequate measured reserve, matching owner/preparation and no active/deleting set. Its short lease is refreshed while all checks remain true; the Watch shows stale/unknown readiness after lease expiry. Starting always rechecks locally; an old “Ready” card is not admission. Background/lock, navigation away, interruption, thermal/storage failure or authority change retires the arm token. A Watch message can wake iOS only in the background and cannot make the camera usable there [A1–A2].

**Start:** Watch requires fresh wrist/crown/fit checks and its existing practice prerequisites. Reserve the recording/session IDs and obtain the fresh phone start acknowledgment before admitting motion. Phone begins writing into that session's private staging; acknowledgment reports actual accepted video and audio PTS, not `startRunning`, command receipt or a UI callback. Watch starts through the existing admission path and inspects valid chunks from both required streams. Before granting `motionDurable`, await `engine.snapshot()` after that inspection: the serial writer must have completed all inspected append operations, its completed chunk count must cover those inspected chunks, and the same attempt/generation must still be live and nonfailed with eligible data from both streams. Recheck authority and cutoff at commit. A rename visible before fsync completes, earlier snapshot, stale generation or failed writer cannot grant readiness. Failure after either source begins produces an interrupted partial session, never a successful start.

Exchange those facts with correlated replies. Only after both devices' actual acquisition confirmations and valid clock mapping may Watch show “Video + motion recording” and a short three-second “Get ready … Go” countdown/haptic. Capture is already running during the countdown; it counts toward the unchanged 120-second motion limit and is retained as preroll. Persist the Go marker separately. If either confirmation is missing, stay “Starting / waiting for …”; never count down optimistically. Phone shows its local capture status even if the Watch has not acknowledged. Independent device observations cannot promise atomic simultaneous start or perfectly synchronous UI.

**Stop/timeout/cancel/disconnect:** Watch Stop immediately applies its local cutoff, then requests idempotent phone Stop; phone emergency Stop does the reciprocal action. “Stopping” becomes “Saved on this device” only after actual finalization, file verification and durable manifest update. Combined saved additionally requires both terminal facts; “Ready to review” requires verified motion receipt on phone. A missing reply is unknown, not failure proof or success. Reconciliation reads the same operation/session state and does not create another capture.

Technical defaults to ratify/test: 15-second renewable arm lease; 12-second bounded startup (permission prompts resolved before arming); 2-second control heartbeat with peer status unknown after 6 seconds; 5-second stop acknowledgment deadline followed by visible “Other device not confirmed”. **Owner confirmation: keep recording to the device.** After actual acquisition begins, temporary connection loss does not stop valid local capture: each already-running device continues saving within its own finite limit, displays local recording plus “Other device unknown”, and reconciles later. Watch Stop still stops Watch immediately; if the phone cannot receive Stop, phone continues until its own deadline or local Stop. No stale Start is queued/replayed and reconnect never starts/resumes acquisition. Heartbeat loss is an operational bound, not proof that the peer stopped. Both devices enforce independent local maximum deadlines: Watch retains its 120-active-second cap; phone has a finite startup/preroll allowance plus that cap even if Stop never arrives. Record actual cutoff/reason and coverage on each device; missing peer confirmation leaves completeness unknown. Late data outside cutoff remains excluded under existing engine rules.

Cancellation before acquisition closes preparation without a recording. Cancellation after any acquisition finalizes an interrupted partial record; removal requires the existing explicit delete flow. Relaunch/reboot retires live authority and recovers retained artifacts; it never silently restarts recording. Phone must explicitly stop its AVCaptureSession on interruption/background so Apple's preserved `startRunning` request cannot unexpectedly resume camera use on foreground [A1].

**Pause decision:** Initial combined mode has **no Pause/Resume**: Stop and start a new set. Disable it in both controls and adapter admission, including practice-level Pause while a combined set is active. An unsolicited native workout pause interrupts the combined set. Existing motion-only pause/resume stays unchanged: its writer/Health acknowledgment mechanism cannot safely be reused as proof that camera and media timelines also paused. Multi-segment pause is a separate reviewed scope increment.

## 4. Timestamp and synchronization contract

Use `AVCaptureVideoDataOutput` plus `AVCaptureAudioDataOutput` feeding a bounded serial `AVAssetWriter` pipeline. Use sample-buffer presentation timestamps and the capture session's `synchronizationClock`; all output timestamps use that timebase [A3–A4]. Do not align a movie using `Date()`, Watch command arrival, recording delegate notification, frame number divided by nominal fps, or the first UI timer tick. Save first/last **successfully appended** PTS per track, rational timescale/epoch, session source time, actual frame intervals/drops, capture-clock identity and mappings. `AVAssetWriter.startSession(atSourceTime:)` determines the source-time origin; verify resulting asset track time ranges/edit timing before deriving player time [A5].

Watch `CMLogItem.timestamp` is seconds since Watch boot [A6]. Existing `RecordingClock.domainID` identifies the recording's source domain; retain it. Establish phone host-clock ↔ capture-clock conversion with Core Media clocks (`CMSyncConvertTime`/supported clock conversion); bracket any host-clock ↔ `systemUptime` reads and preserve their uncertainty. Do not assume audio clock, host clock and system uptime are numerically interchangeable. Test clock conversion against the actual SDK; unavailable/discontinuous mapping blocks combined Go, while retaining partial data.

Cross-device exchanges record four monotonic values: phone send `p0`, Watch receive `w1`, Watch reply `w2`, phone receive `p3`, with request and both epoch identities. For offset `Watch − Phone`, under monotonic compatible rates the observation interval is `[w2 − p3, w1 − p0]`; midpoint is an estimate, interval width exposes asymmetric transport uncertainty. Persist every accepted/rejected observation and round-trip duration. Use a small bounded series at arm/start and periodically/stop; reject stale epochs, negative elapsed times, reordered pairs and nonfinite values. Fit/recheck an affine offset/rate map only with sufficient separated observations, retaining residuals and coverage. If evidence cannot support a drift estimate, do not fabricate zero drift or extrapolate beyond supported coverage without visibly increasing/unknown uncertainty.

Compose Watch sample → phone host → capture PTS → verified player time. Show “Estimated alignment” and its evidence/uncertainty; synchronization is not guaranteed frame accuracy. A visible/audible simple racket tap at the beginning/end supplies a manual check of correspondence, not an assumed precise sensor event. Let the owner adjust alignment during replay through a versioned offset revision with original estimate, correction, author, timestamp and reason. It never changes raw timestamps. Where uncertainty/discontinuity prevents defensible matching, allow separate playback/charts and unmatched labels, disabling a misleading linked playhead. Ratify an engineering display threshold from device observations; do not invent a measured accuracy target.

## 5. Durable media, mixed attempts, privacy and recovery

Keep video/audio on the iPhone; continue using existing Watch raw archives and verified receipts for motion. Versioned `VideoMotion-v1` sidecars are indexed by immutable owner/practice/session/recording IDs, with schema, source/build identity, original acquisition/Go/stop facts, clock observations/mapping revisions, media entries/digests/PTS spans, raw receipt and per-component states. Old raw recordings and old exports remain readable. A combined record may exist before motion arrives and must show “Motion pending” rather than claim completeness.

Use app-private staging and atomic manifests with existing safe filesystem conventions, explicit bounds and deletion fences. An AVAssetWriter “append succeeded” is accepted input, not a crash-durability guarantee. Write short independently finalized media segments (initial target 5 seconds; each starts at a decodable keyframe), fsync/verify their manifest entries, and assemble them for continuous AVPlayer replay. Bound finalization backlog; never accumulate unbounded buffers. The active segment can be lost/unplayable after process termination: retain it as unverified, recover only demonstrably playable data, and display actual retained coverage/gaps. Never rename an incomplete movie and claim it saved. On orderly Stop finalize the tail, verify audio/video tracks and durations, then publish. Segment rollover must preserve source PTS continuity and report dropped/unwritten samples. This durability choice needs native proof before court use.

No automatic raw deletion after transfer. Keep original audio/video, motion and revision history until explicit owner deletion. No Photos save, Drive upload, cloud sync or other external publication by this increment. Mark new private capture/staging/export files excluded from cloud backup; review existing backup semantics without changing baseline data policy silently. Denial, unavailable storage, protected-file access, out-of-space/thermal failure and corrupt/truncated media yield truthful partial/interrupted results. Preflight storage reserve is based on configured maximum media bitrate, duration and staging overhead; measure actual bytes/minute and energy/thermal behavior before ratifying a smaller budget. Do not silently reduce sample rate, resolution or audio.

New per-attempt annotation records have: schema version, attempt ID, revision/parent revision, session/recording IDs, video interval and explicit media timebase, optional matched Watch interval/domain and mapping revision, stroke `{forehand, backhand, unclassified}`, contact `{clean, mishit, unsure}`, owner-self provenance, evidence `{audioAndVideo, video, ownerRecall}`, note, creation/edit times, and deletion/tombstone state. Missing/unmatched evidence remains explicit. A fresh attempt is **unclassified/unsure**, never inferred from the set's drill. Support multiple mixed strokes in one set. **A0 introduces an explicit versioned `videoMotionMixedReference` capture mode in accepted preparation and immutable recording context**, included in their validated identity/digest; combined mode accepts only truthful `otherUnclassified` raw intent with the new mixed-reference protocol identity. It cannot be inferred from a UI flag, `otherUnclassified` alone, or a sidecar attached after admission. Mode changes require a new accepted preparation identity and fresh physical confirmation. Legacy/motion-only preparation still accepts only its existing forehand/backhand intents, with byte-compatible historical decoding/identity and no raw migration. UI calls the new mode “Mixed forehand + backhand”; it never presents the whole mixed set as Forehand. Human labels are not detected strokes or independent ground truth.

Revision writes compare the expected latest revision, retain conflicts and history, and are atomic. Audio remains unchanged; an edited label does not rewrite spoken words. Legacy contact labels display as legacy/unclassified unless the owner explicitly annotates an attempt. Repeat-label review can hide earlier labels; model training and formal evaluation are outside this increment.

Private export previews exactly included raw motion, original media/audio, mappings, annotation history, schema/units and SHA-256 manifest; explicit omission of media must be labelled. Re-read/validate the prepared archive before sharing; owner/consent/deletion fences apply through publication. No exporting active/unfinalized recordings as complete. Whole-practice deletion must stop/release capture/player resources, tombstone against late arrivals, remove final/staging/orphan media, mapping/annotation/cache files and prepared exports, then use existing paired deletion acknowledgments. Keep “paired deletion pending” while offline; independent copies previously exported remain outside app control. Withdrawal immediately retires arm/capture and closes video/chart analysis consistently with existing policy.

## 9. Decisions and sources

**Already approved scope:** Watch-controlled phone video/audio and wrist motion, foreground phone preparation, truthful combined status, iPhone replay/analysis, owner-edited labels; existing owner/platform/theme/duration baseline. Latest owner confirmation “yes, just keep recording to the device” means local iPhone video/audio and Watch motion with paired-phone transfer, continued already-running local capture through connection loss, and no automatic cloud upload.

Ratify after independent challenge; revise defaults if native evidence contradicts them. This does not reopen owner approval for the requested feature.

**Requires a new owner decision only if needed:** longer sets/full matches, silent/no-audio combined mode, background/locked-phone camera expectations beyond supported foreground workflow, automatic visual/quality assessment, transcription/cloud services, importing/sharing third-party media, guest collection or external retention/publication. Any major architecture/privacy change resulting from an unavailable API returns to plan/approval. No such dependency is required to start A/B.

Primary Apple documentation checked 25 October 2026; implementation must verify the actual selected SDK and physical behavior:

- **[A1]** [AVCaptureSession background-camera interruption](https://developer.apple.com/documentation/avfoundation/avcapturesession/interruptionreason/videodevicenotavailableinbackground): background camera prohibition and preserved start request explain the foreground requirement and explicit stop on interruption.
- **[A2]** [WCSession.sendMessage](https://developer.apple.com/documentation/watchconnectivity/wcsession/sendmessage(_:replyhandler:errorhandler:)) and [Watch Connectivity](https://developer.apple.com/documentation/watchconnectivity): asynchronous interaction/wake behavior does not grant foreground camera access or guaranteed delivery.

- **[A4]** [CMSampleBuffer presentation timestamp](https://developer.apple.com/documentation/coremedia/cmsamplebuffergetpresentationtimestamp(_:)) and [CMSyncConvertTime](https://developer.apple.com/documentation/coremedia/cmsyncconverttime(_:from:to:)): use sample/media clocks, preserving valid timescales and epochs.
- **[A5]** [AVAssetWriter.startSession](https://developer.apple.com/documentation/avfoundation/avassetwriter/startsession(atsourcetime:)) and [finishWriting](https://developer.apple.com/documentation/avfoundation/avassetwriter/finishwriting(completionhandler:)): source-time session and actual completion are distinct from command/callback receipt.
- **[A6]** [CMLogItem.timestamp](https://developer.apple.com/documentation/coremotion/cmlogitem/timestamp): source measurement time is seconds since device boot.
