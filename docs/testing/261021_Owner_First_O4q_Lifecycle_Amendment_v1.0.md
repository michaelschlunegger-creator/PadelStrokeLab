## Durable fact and identities

Add one optional, bounded phone lifecycle record to the existing canonical channel journal and expose its checked immutable value in `OwnerChannelSnapshot`. Fields: independent `practiceID`, independent `preparationID`, `ownerID`, `phoneEpoch`, `watchEpoch`, optional stable local `endRequestID`. The two practice/preparation IDs must differ. This record is bookkeeping and local denial, never consent, accepted setup or a second dispatched authority command. Reopen may expose it only with the existing live channel/O2 checks; UI acceptance and Start still require a fresh reviewed preparation exchange.

`beginPhonePractice(practiceID:preparationID:owner:)` takes an exact checked owner identity. It accepts only the current reconciled identity, or the exact retained enrollment proposal while current authority is nil. A new record requires collection consent in that current/proposed identity, distinct IDs, an unretired practice ID and ordinary channel capacity; a non-enrollment pending intent prevents creating a new lifecycle. Persist the record before saving its P1 draft and before any preparation carrying the practice ID may leave the phone. A matching retry is idempotent while End is absent, including while a later non-enrollment intent is pending; a different unresolved practice/preparation/scope or an End-pending retry cannot replace/reopen it. Later same-practice edits preserve both IDs and advance P1's global draft revision. New practice IDs are independently created after proven retirement; no P1 ID aliases a practice ID.

Derivation checks phone role, local epoch, distinct IDs, exact owner/phone/Watch scope and the record's byte bound against the derived current owner or retained nil-authority enrollment. A mismatched record fails closed. A lifecycle record whose only basis is pending enrollment prevents cancelling that enrollment while authority is nil. The cancellation returns an explicit domain failure without changing the enrollment or lifecycle. End may still latch; the original affirmative enrollment may reconcile before retirement. No automatic grant, reconstruction or new owner is inferred from this bookkeeping. Ordinary cancellation without that condition retains its existing behavior.

## End, ordering and retirement proof

`requestPhoneEnd(practiceID:requestID:)` durably latches the stable local End request despite an occupied or dispatched authority intent. Exact duplicates are idempotent; another practice or request ID conflicts. The phone admission flag becomes blocked, but motion/HR consent and existing privacy fences keep their original meanings. This API never cancels, rewrites, dispatches or reconciles the occupied command. O4b must fence presentation before the executor hop; failed persistence must remain visibly blocked without claiming End was saved or applied remotely.

`queueRequestedEnd() -> OwnerAuthorityMutation` requires the retained End latch and reconciled current authority. It creates the existing `retirePractice` mutation only when the single authority-intent slot is free. An already queued exact-practice retirement returns the same retained wire command if it is not obsolete; an obsolete one requires the existing explicit resolution, and an unrelated intent remains outstanding. Its wire mutation ID is independently generated and is **not** the local `endRequestID`. Exact wire retry uses the retained existing intent. If intervening verified authority makes that command obsolete, only the existing explicit resolution rules may replace it with a fresh wire mutation ID; the stable local End request and exact practice ID remain unchanged. No automatic rebase, timeout cancellation, status grant or second dispatched command is added.

Clear the lifecycle record only when a retained, verified chain transition retires its exact practice and a live O2 check confirms that practice's replay guard after reconciliation. Clear it atomically with the phone checkpoint where possible. If an unrelated obsolete intent requires the current checkpoint's early-return path, commit the lifecycle clearance while preserving that unpruned chain and intent; do not silently lose the proof or erase the intent. Reopen replays the same exact chain/O2 ordering. A grant, withdrawal, unrelated retirement, ACK, cancellation, timeout or guard alone cannot clear it. Clearing does not remove an existing privacy fence, restore acceptance or grant consent. A new practice cannot replace an unresolved lifecycle record.

## Canonical compatibility and capacity

The new journal field is optional and omitted when nil. Existing settled v2 canonical bytes therefore remain readable and unchanged; the existing accepted replay/checkpoint recovery may still write. There is no namespace/version rewrite or migration. The existing `OwnerCanonical` decode/re-encode equality checks checksum and exact bytes: a legacy decoder that lacks the field must reject an expanded record instead of discarding it. Tests use a faithful old journal shape through the actual canonical decoder to prove both properties, including old pending intent and anchored states. Explicit null, unknown, malformed, oversized and scope-mismatched lifecycle fields are rejected.

The whole non-nil lifecycle record is at most512 canonical JSON bytes. While its End field is absent, reserve64 additional envelope bytes on every journal encode, enough for the optional UUID property; tests prove the actual increase stays within the reserve. This protects End-latch publication from other valid journal growth. Beginning a record also requires normal channel capacity. Queueing retirement still uses the existing one-intent journal bounds and Watch End reserve; it cannot claim success after byte/revision exhaustion. An End latch itself does not increment authority and may remain durably pending if later retirement cannot be queued/applied. Full/ambiguous storage remains blocked without reset, eviction or false saved/applied claims.

For a meaningful boundary test, add a constructor-only **internal**, immutable-per-owner `maximumJournalBytes` limit defaulting to the existing production maximum. Accept only positive values no greater than the production cap; validate before filesystem creation. Thread it through the actual encoder/commit and applicable capacity calculation, with no public alternative API, codec or validation path. Tests reopen with the same stricter limit. This seam may only restrict capacity, never relax production bounds. Demonstrate that normal growth refusal preserves a healthy owner while the reserved End latch succeeds durably and reopens; test an insufficient limit and invalid limits without claiming anything was saved or applied. Observed compact transition sizes alone are not treated as a proven lifetime bound or boundary-test substitute.
